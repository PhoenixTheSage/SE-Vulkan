# Plan: meet or beat DX11

Goal: private Pertam, 1080p, product defaults. Present cadence **below 4.17 ms
on both mean and P95**, in three both-order pairs, with parity gates unchanged
(see `PERFORMANCE_STRUCTURAL_PLAN.md`, final acceptance).

Started 2026-10-25; rewritten 2026-10-26 after sessions 1–6 and scheduler
steps 1–5. History, measurements and run IDs are in
`Docs/Performance-2026-10-25-Attribution.md`.

## How a frame is gated today

Pipelined recording: frame N's managed `Draw` runs on the render thread while
frame N−1 records on the recording thread, and frame N−2 presents on the
present thread.

- **Recording again (the wall since step 6).** Step 6 cut 1 ms of
  render-thread work ahead of publication, so the render thread now reaches
  publication's first ordinary native call about 1 ms before recording
  releases `api_mutex`. Below, the render thread's own work (step 5 numbers;
  step 6 removed about 0.6 ms of traversal):

  | Phase | ms |
  |---|---|
  | Scene update and traversal | about 2.7 |
  | Native pass publication | about 1.0 of CPU work |
  | QueueWorld | 0.6–0.7 |
  | Messages | 0.4 |
  | Particles | 0.3 |
  | Lighting setup | 0.25 |
  | Sprites and the rest | — |
- **`api_mutex`.** Recording holds it for all of `end_frame`, now about 4.1 ms
  after launch. The render thread's first ordinary call is the fresh probe
  read at publication, and it still waits about 0.5 ms per frame there.
- **Present.** `vkQueuePresentKHR` holds a driver lock while it runs. Since
  present-after-GPU, the call takes about 1.1 ms and stalls little.
- **GPU.** About 2.9 ms; not a wall.

To reach 4.17 ms, the render thread must lose about 3 ms of work, and
recording must stay under it.

## Next, ranked

### 0. Decouple or shorten recording (the wall since step 6)

Render-thread cuts no longer move the cadence until this is done.

- **1c, recording state outside `api_mutex`.** Publication (`sevk_pass_prepare`,
  `sevk_pass_publish`, cell publish) and `QueueWorld` mutate state that
  recording N−1 reads. That covers:
  - pass scene render groups and instance streams;
  - cell emitted draws;
  - `world.current()` draws, objects and orders;
  - probe state.

  Double-buffer that state per frame, and swap at `end_frame_async`. The
  render thread then publishes frame N while recording reads N−1, and the
  about 1 ms lock wait disappears. Audit every ordinary call that runs
  between `BeginFrame` and `EndFrameAsync`, and every state `end_frame`
  reads.
- **Shorter recording**, worth about 1 ms:
  - spot shadows 0.66–0.74 ms: each light scans every draw; bucket draws
    spatially once per frame;
  - NEW main 0.63–0.69 ms: 3.1, with its prerequisites below;
  - prepare pass streams 0.40 ms: per-group lookups; persist per-group offsets
    and material sets while the group set is unchanged.

### 1. Remove render-thread work (after 0)

- **1a, actor traversal and scene update.** The candidate query is gone
  (step 6): traversal 0.92 → 0.35 ms. What remains is per-actor work for
  about 1,000 managed actors, plus the scene update (about 1.1 ms of real
  changes).
  - Generalize 2.1 emitters to carry main-group, owner and OLD-order scope,
    then run the traversal in parallel chunks spliced in order.
  - 2.4: make the scene update touch only changed actors (spatial index
    0.26, transforms 0.15–0.19, shadow poses 0.15, occlusion 0.25–0.30).
  - Profile again first: the traversal split moved after stable main order.
- **1b, native pass publication (about 1.0 ms of CPU in prepare and
  publish).**
  - This is CPU-only selection behind `api_mutex`.
  - Early prepare (session 6) moved it onto a worker and still did not pay
    in the step 5 option set.
  - Make the selection incremental (O(changes)) instead of moving it.
- **1c, QueueWorld (0.6–0.7 ms).** Blob packing and native queue intake;
  retained submission already covers part of it. Attribute again.
- **1d, particles (0.33 ms).** Not forkable as is: their light hooks
  create, destroy and update scene light actors, and read parent world
  matrices that the scene update rewrites. A fork needs buffered light
  commands applied before `SubmitLights`, and can only overlap the shadow fit
  and voxel plan launch.
- **1e, allocation, third pass.** About 400 KB per frame in Draw; GC tails
  drive P95.

### 2. Keep recording under the render thread

Recording ends about 4.1 ms after launch. Once the render thread gets
faster, this becomes the wall again. Recording laps (ms per frame):

| Lap | ms |
|---|---|
| Prepare materials and pass GPU prep | about 0.7, now split into two laps |
| GBuffer NEW main | 0.66 |
| Spot shadows | 0.40 |
| Prepare sort | 0.31, now reused when keys are unchanged |

- **3.1, parallel NEW main recording.** Prerequisites:
  - precompute GBuffer velocity offsets in prepare (today a running cursor
    assigns them in record order);
  - per-worker descriptor pools for the main pass;
  - frame marks lifted out of the draw loop.
- **Recording state outside `api_mutex` (the original step 4 idea).**
  Ordinary render-thread calls that touch only scene state would stop
  serializing behind `end_frame`. Do this when the lock census shows the
  render thread waiting again.

### 3. Phase 4: frame-build stage

The render thread does messages and changes; a worker builds frame N while
recording runs N−1. Worth it only once 1 has cut the render-thread work, and
it still needs recording under budget.

## Designs for the large remaining items

These need their own sessions. Each design lists the shared state that blocks
it today and a gate.

### 1a, parallel actor traversal

Shared mutable state in the traversal loop, found 2026-10-26:

- main-group, packet-owner, logical-owner and OLD-order scopes on
  `NativeBackend`;
- rigid and model batching dictionaries, finalized at `QueueWorld`;
- bulk native models;
- prepared-submission replay lists;
- glass, decal and highlight packet lists;
- spot-shadow marking (`MarkSpots`);
- the visible set;
- group-occlusion queries;
- LOD and size-cull counters;
- texture lookups (resident-only reads now exist);
- recipe resolution (the slow path is now locked).

Design:

1. Extend `PacketEmitter` to carry scope state. Each emitted packet records
   the main group, part, OLD order and owner it was emitted under.
   `SpliceEmitter` then accepts scoped emitters and assigns orders in splice
   order.
2. Give each chunk its own batching dictionaries, glass and decal lists,
   spot marks and counters. Merge them at splice in chunk order, so the
   merged state equals serial traversal.
3. Split the candidate list into contiguous chunks (it is already planned in
   parallel by `PlanCandidates`). Run chunks on `RenderJobs` and splice them
   in order.
4. Gate on the packet signature in the frozen-light lane, plus glass, decal
   and highlight counts.

Expected: the managed traversal (about 0.6 ms after the index change) mostly
overlaps.

### 1b, incremental native publication

`sevk_pass_prepare` and `sevk_pass_publish` (about 1.0 ms of CPU each frame,
already fanned out over view jobs) recompute selection, LOD and batches for
every native actor in every view each frame. Design:

- Keep per-actor per-view selection results.
- Recompute only actors whose pose, appearance, LOD band or view relation
  changed. View relations change with the camera, so bucket actors by cell
  and recompute the cells that crossed a view or LOD boundary.
- Rebuild batches only for changed (model, view) keys.
- Gate on the native-pass lane and NativePassGpuTests.

`SE_VULKAN_VIEW_LANES` is the cheap version: more lanes on the same work.

### 3.1, parallel NEW main recording

Prerequisites:

1. Compute GBuffer velocity offsets in prepare, per draw, instead of the
   running cursor in `gbuffer_velocity_draw`.
2. Per-worker descriptor pools for main-pass forward and stock sets (spots
   already have them).
3. Frame marks and CPU laps outside the per-draw loop.

Then split the ordered entries of `record_new_main` into contiguous ranges,
record each into a secondary with inheritance rendering info, and execute
them in order. Gate on GBuffer readbacks in WorldPassGpuTests and the
frozen-light lane.

### Phase 4, frame-build stage

- The render thread keeps message processing, scene changes and the native
  commits.
- A frame-build worker runs the traversal, voxels and effects (already
  forked), publication and `QueueWorld` for frame N, while the render thread
  processes frame N+1's messages.
- Requirements:
  - an immutable per-frame actor snapshot for managed fallbacks (glass,
    skinned, OLD decals); native-owned actors are already snapshot through
    commits;
  - `NativeBackend` emission state per frame;
  - an input-latency measurement and a toggle.

### Smaller and parked

- **Job pool queue wait (30–40 µs):** not caused by waking a sleeping worker;
  spinning did not change it. Attribute (thread scheduling, or the stats
  path) before changing anything.
- **GPU margin (about 2.9 ms against a 3.6 ms budget):** every new pass
  needs GPU pass timing and a consumer gate.

## Lessons

- **Find the wait before moving work.** Work removed ahead of a blocking
  point only lengthens the wait (sessions 5–6, steps 1–3).
- **Gates move, they don't vanish.** Each fix in steps 4–5 exposed the next
  gate. Only time lock acquisition and stage boundaries reveal them.
- **Counters can miss waits.** The pipelined-wait counter read 0 while calls
  blocked on `api_mutex`.
- **Driver locks are real.** A slow `vkQueuePresentKHR` stalled unrelated
  Vulkan calls on other threads.
- **Averages need the right population.** Exclude non-pipelined frames from
  pipeline timelines.
- **Caches, byte copies and extra workers around per-frame reconstruction did
  not pay.** Remove the per-frame O(N) work instead.
- **Size candidates with `-CpuDetail` wall phases and the pipeline report**
  (`SE_VULKAN_PIPELINE_REPORT`): lock census, call census, deferred replay,
  `begin_frame` laps and timeline. Confirm with paired runs in both orders.
- **Pinned-baseline benchmarks run the HEAD harness against old plugins.**
  Keep new-API hooks isolated (memory note `harness-pinned-baseline-compat`).
- **Judge lighting only in the same-process frozen-light lane.** Pertam has a
  flashing light. Billboards need the self-check instead. The packet
  signature cannot gate changes that reorder candidates (the index change);
  judge those on rendered artifacts.
- **Harness hooks follow method names.** When a product path stops calling a
  hooked method (`SetProbes`), route it through a hookable public method, or
  the lane silently loses its freeze.
- **Check for Codex activity before any timing run.**

## Method

1. Profile first: `-CpuDetail` plus `SE_VULKAN_PIPELINE_REPORT=<path>`.
2. Judge throughput by the present interval mean, never `CpuMeanMs` alone.
3. Paired interleaved runs in both orders (X, Y, Y, X); single runs vary by
   about ±0.4 ms. Normalize across days with a DX11 run.
4. One toggle per change; default on only after its gates pass:
   - packet signature or self-check where output order matters;
   - the frozen-light lane for lighting;
   - focused GPU suites under validation;
   - a validation gameplay run.
5. Implement a batch, then test and benchmark it once.
6. Product-default flags: `-ActorLods -AsyncPresent -NewActorViews
   -RetainedSubmission -StockShadowSchedule -StockShadowFit -WorldRecipes
   -ParallelQueue -ParallelCascades -NativePassScene -GroupOcclusion
   -StockDepthGeometry -NativeCells -NativeMixedOpaque -PipelinedRecording
   -AsyncPassPacking -DeferredCellEmission`.
