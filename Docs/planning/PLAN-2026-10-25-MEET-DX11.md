# Plan: meet or beat DX11

**Goal.** Private Pertam, 1080p, product defaults. Present cadence **below
4.17 ms on both mean and P95**, in three both-order pairs, with parity gates
unchanged (`PERFORMANCE_STRUCTURAL_PLAN.md`, final acceptance).

**Ground rules (user decisions):**
- Fixes live in the renderer. Nothing may depend on the player changing driver
  or system settings.
- No present-type switching (no own DXGI swapchain). Overlay layers (Steam,
  EOS, Fossilize) are not worth investigating.
- DX11 and Vulkan develop in parallel through Anomaly; Vulkan-only work is
  allowed only when the feature can't exist on DX11, and is documented as such.
- Commit and push to `main` only.

**Other documents:**
- `PLAN-2026-10-25-MEET-DX11-history.md`: the full earlier plan (Phase 4
  milestones 1–6 as built, Plan 2, step history, old designs, evidence lists).
- `Docs/Performance-2026-10-25-Attribution.md`: every measurement, batch and
  run ID.

## Where we are (2026-10-30)

Split (`SE_VULKAN_FRAME_SPLIT=1`) **4.72–5.10 ms** against DX11 **4.22–4.36**,
depending on the session. The benchmark is windowed on a 240 Hz monitor:
4.17 ms is one refresh, and DX11 sits at it. Beating it means presenting
faster than the refresh (mailbox).

Three chains each take about 4.5–4.7 ms, and shortening one hands the frame
to the next:

| Chain | Cost per frame | Notes |
|---|---|---|
| **Build thread** (paces in 2026-10-30 sessions) | about 4.3–4.5 ms own work | publication 1.3, `QueueWorld` 0.84, scene build about 1.6, voxels and billboards 0.41, prologue 0.30, lighting setup 0.15 |
| **Recording stage** | laps about 3.5–3.7 ms, submit blocked 0.25–0.4 behind the present lock, lock re-acquire about 0.1, launch gap 0.35–0.9 | the gap grows by exactly what the laps shrink while Build paces |
| **GPU + present** | GPU frame 2.35–2.7 ms, then a 1.3–1.5 ms present call | the present call waits for the GPU and blocks other threads' submits; a standalone probe of the same present structure takes 0.2 ms (cause open) |

**Measurement caveat.** Across one evening the same code's GPU frame drifted
2.35 → 2.70 ms, recording laps about 10%, and DX11 4.22 → 4.36 ms. Changes
under about 0.15 ms are readable only in same-session interleaved A/B runs.

## How a frame flows today (split on)

| Thread | Frame | Work |
|---|---|---|
| Render thread (game) | N+1 | `ApplyFrame`: messages, particles and decals, scene update, billboard collection, probe ambient. Then `JoinBuild`, publish the visible set, `Handoff` (latches), launch Build. |
| Build thread ("Vulkan frame build") | N | `BuildFrame`: prologue, clipmaps, shadow fit, scene build and traversal, voxels and billboards, lighting setup, native pass and cell publication, `QueueWorld`, `EndUploads`, `BeginFrame`, sprites, `RaiseFrame`, `EndFrameAsync`. |
| Recording stage (native) | N−1 | Records the frame's command buffer. Releases `api_mutex` early once it has snapshotted scene state (`rec_view`), so Build's scene calls run during the recording. |
| Present worker (native) | N−2 | Decoupled present: acquire, copy the per-slot output image into the swapchain on the present queue (async compute family), wait for the copy, `vkQueuePresentKHR`. |

**Mechanisms that matter when changing anything:**
- **Deferred calls.** While a recording is in flight, ordinary native calls
  are queued (`call_deferrable`) and replayed by the next ordinary call;
  scene calls (`call_scene`) run once the recording has released. A deferred
  call that changes what scene calls see must itself be a scene call.
- **Build waits for the previous recording only in `EndUploads`**, just
  before `BeginFrame`. The upload batch is global; Build owns it.
- **Launch snapshot.** `EndFrameAsync` publishes shadow, occlusion, flare and
  probe feedback for Build's next reads (`publish_launch_snapshot`).
- **Async OLD-cell emission** starts at `QueueWorld` (`EmitCells`) and is
  joined by the next native call (about 390 µs of work).
- **Scene owner checks.** One thread owns scene calls; the frame gate makes
  other threads' calls wait while a frame is open
  (`SE_VULKAN_FRAME_GATE`, on with the split).
- **Actor snapshots.** `ActorFrame` has two parity slots: Apply writes one
  (dirty actors only) and Build reads the other (`BuildFrameOf`).
- **Guest callbacks** (`RaiseScene`, `RaisePreparation`, `RaiseFrame`) run on
  the build thread under the split. The contract proposal is in Anomaly
  `wiki/Framework-gaps.md`.

## Plan 3: a two-stage build (design 2026-10-30; milestones 1–2 done, milestone 3 next)

### Why

Build paces the split at about 4.3–4.5 ms of its own work. Single-phase
trims are worth about 0.1 ms, below the box's drift. Overlapping publication
inside one Build failed (6.1–6.3 ms). A second build stage takes half of
Build off the critical chain.

### The split

Four threads, one frame each, pipelined. The line runs between managed scene
work and native scene work:

| Thread | Frame | Work |
|---|---|---|
| Render thread (Apply) | N+2 | unchanged |
| **Build stage A ("scene")** | N+1 | prologue, clipmaps, shadow fit, traversal and packet emission, voxels and billboards, lighting setup, group occlusion queries, and the managed half of publication: pass and cell commits **captured**, not sent |
| **Build stage B ("native and launch")** | N | replay of A's captured native calls (commits, setters), native pass and cell preparation and publication, fallback emission, end visibility, `QueueWorld`, `EndUploads`, `BeginFrame`, sprites, `RaiseFrame`, `EndFrameAsync` |
| Recording stage | N−1 | unchanged |

**Estimated sizes** (2026-10-30 CpuDetail session):

| Stage A | ms | Stage B | ms |
|---|---|---|---|
| Prologue (packet collection) | 0.30 | Replay of captured commits and setters | about 0.15 |
| Clipmaps + shadow fit | 0.19 | Native preparation join | about 0.1–0.3 |
| Scene build: traversal, transforms, lights, shadow poses, legacy and skinned actors | about 1.6 | Native pass publish | 0.77 |
| Voxels and billboards | 0.41 | Cell publish | 0.20 |
| Lighting setup | 0.15 | Fallbacks and end visibility | about 0.12 |
| Commit capture and group queries | about 0.2 | `QueueWorld` (pack and native queue) | 0.84 |
| | | `BeginFrame`, sprites, guest frame, launch | about 0.2 |
| **Total** | **about 2.8** | **Total** | **about 2.4–2.6** |

Moving voxels and billboards to B flips the balance to about 2.4 / 2.9; it's
a later tuning knob. They stay in A by default because A's occlusion
revision reads their mesh updates.

**Why this line.** Native publication is the heaviest remaining work, and its
inputs already arrive through deferrable scene calls (commits are
`call_deferrable_scene`). Capturing A's calls per frame and replaying them in
B reuses that mechanism. Publication's managed reads (group occlusion results,
LOD) stay in A. B needs per-actor state only for fallback emission.

### What has to be per-frame

**Managed:**
1. **`FrameEmission`** (milestone 3 of Phase 4 skipped it). It holds:
   - world, highlight, decal, glass, transparency and billboard packets;
   - main groups and scopes, rigid and model batches;
   - shadow exclusions and `CameraPosition`.

   A fills emission N+1; B adds fallback packets to and packs emission N.
   Single-thread runs keep one emission. Tests reflect on `worldPackets`, so
   keep the field's object stable there.
2. **Three actor-snapshot slots** instead of two parity slots. Apply writes
   N+2, A reads N+1, B reads N. Dirty refreshes must reach every slot as it
   rotates; verify mode (`SE_VULKAN_FRAME_PACKET_VERIFY=1`) checks it.
3. **Sprites:** a third main buffer.
4. **The visible set** comes from B's end visibility, so the game sees it one
   frame later than under today's split. Check LOD and animation decisions.
5. **The upload batch.** A uploads while B flushes. A's batch is sealed at the
   A→B hand-off and submitted by B; A opens the next one (native: separate
   seal from submit on `upload_slots`).

**Native:**
1. **Captured calls.** A's native scene calls for frame N go into a
   frame-tagged list that B(N) replays in order:
   - pass and cell commits, and preparation requests;
   - setters: lights, shadow cascades and matrices, spots, probe, postprocess
     and environment configuration, flare queue, guest products.

   A reads native state only from the launch snapshot (flare and occlusion
   results, shadow and probe feedback, preparation results of the frame B
   last published).
2. **Publication snapshots.** B publishes, then captures pass groups and
   streams and OLD-cell draws into a per-frame slot that recording N binds.
   Today's `rec_view` is taken at recording start, which B(N+1) could already
   have overwritten.
3. **Scene owner:** stage B's thread, the only one issuing scene calls. The
   census must show 0 off-owner scene calls.

### Milestone 2: three actor-snapshot slots (built 2026-10-30)

- `ActorData.Frames` has three slots that rotate with the latch:
  - Apply writes `applyParity`;
  - Build reads `buildParity`;
  - the slot Build read last frame stays intact as `launchParity`
    (`LaunchFrameOf`, for stage B).
- Dirty history covers two frames (`frameDirtyPrevious`,
  `frameDirtyEarlier`). An actor refreshed at frame f catches up in the next
  two slots by copying the previous slot, which is always current.
- Snapshot and latch run under the same condition, so slots never advance
  without a refresh.

**Open for milestone 3: fallback emission reads more than `ActorFrame`.**
Stage B's fallback packets also need the actor's model, materials and LOD,
which the latch folds into `ActorData` for the next frame while B runs.
Before stage B emits fallbacks, either capture those per frame or check how
rare fallbacks are and whether a one-frame miss is acceptable while models
stream.

### Milestone 1: `FrameEmission` (built 2026-10-30)

**As built.**
- New file `Rendering/Interop/NativeFrameEmission.cs` holds the
  `FrameEmission` class.
- `E` returns the thread-bound emission, otherwise `current`.
  `InitializeEmissions` runs in the backend constructor.
- Every per-frame field access in `Rendering/Interop` goes through
  `E.<Field>`. The public names (`CameraPosition`, `MainPart`,
  `DecalPackets`, `BillboardPackets`, `ShadowExclusions`,
  `LogicalRigidDraws`) are now forwarding properties.
- The private fields `worldPackets` and `glassPackets` remain as aliases of
  the current emission's lists, for tests that reflect on them.
- Rigid batch hints and main-group key caches record the emission as their
  owner.
- Batch frame numbers come from a backend counter, so they are unique
  across emissions (model batches compare against them).
- The gate is `SE_VULKAN_EMISSION_ROTATE=1` (scene property
  `EmissionRotateEnabled`). It switches emission at every
  `BeginPacketCollection` and carries the camera over.

**Deliberately left on the backend** (Plan 3 requires the first two off,
and both are off by default; the rest are revisited in milestone 3):
- model batching (`SE_VULKAN_MODEL_BATCHING`);
- bulk models (`SE_VULKAN_BULK_MODELS`);
- pending resident-owner changes. They can happen between frames, so
  per-emission copies would flush out of order;
- the logical-selection capture (diagnostic).

**Design and inventory (2026-10-30).**

**Binding, not swapping.** Under two stages, B emits fallback packets for
frame N while A emits frame N+1. Every `AddWorldPacket` path reads and
writes scope state, so one swapped field set can't serve both threads.
Instead:
- `NativeBackend` holds a default emission;
- a `[ThreadStatic]` binding selects the calling thread's emission, falling
  back to the default (the pattern `PacketEmitter` already uses);
- every per-frame field access goes through it (`E.`).

Single-thread behaviour is unchanged. The gate is a same-process toggle
that alternates two emissions every frame: packet signature, glass and
billboard signatures must stay identical, which proves no per-frame state
leaks between frames through the backend.

**Per-frame state that moves into `FrameEmission`:**

| File | State |
|---|---|
| `NativeBackend.cs` | `frameMeshes`, `collectingPackets`, `CameraPosition` |
| `NativeWorld.cs` | `worldPackets`; the recycle precollection (`precollected`, `precollectedFor`) |
| `NativeMainGroups.cs` | `mainGroups`, `mainGroup` (current scope), `mainGroupEpoch`, `MainPart`, `mainOwnerIds`, `mainOwnerGroups`, `mainGroupPool`, `mainGroupsRented`; the pending resident-owner changes (`residentSets`, `residentRemovals`). `stableOrders`, `nextStableOrder` and `residentOwners` stay persistent (A-owned). |

Each `RigidBatch` carries per-frame `Frame`, `PacketIndex` and the `Instances` array the packets point at, so each emission owns its own cache. `RigidBatchHint.Owner` becomes the emission. |

**Pack-side scratch** (`instanceOffsets`, `constantArena`, `instanceArena`,
`drawScratch`, `recipeScratch`, `objectIdentityScratch`, `mainOrderScratch`,
`oldOrderScratch`, `drawOwnerScratch`, the recycle scratch arrays and job)
is used only by `QueueWorld`, which is stage B. It stays on the backend,
because only B packs.

**Native calls hidden in emission (for milestone 3):**
- `BeginPacketCollection` sends native queue clears: world, decals,
  highlights, transparency, environment, foliage, occlusion, exclusions and
  the pass frame. Under two stages they belong to B's sequence.
- `EnsureWorldRecipe` registers recipes natively, synchronously, from A's
  emission. It is a resource call like an upload, not a per-frame input, so
  it stays a direct call; check that it never waits on B's open frame.

### Guests and DX11

- `RaiseScene` and `RaisePreparation` run on A and `RaiseFrame` on B, so one
  frame's callbacks span two threads. Extend the Anomaly contract note:
  callbacks must not assume one thread per frame.
- DX11 is unchanged. Vulkan-only, opt-in: `SE_VULKAN_BUILD_STAGES=2`.
- Input latency grows by one more frame (about 4–5 ms). Measure it before any
  default.

### What it buys

- Each build stage is about 2.4–2.8 ms, so Build stops pacing, with room for
  drift.
- The recording chain then paces at about 4.4–4.6 ms. The cuts already in
  place start to pay:
  - async submit (opt-in), about −0.3 ms;
  - parallel prepare and early NEW main entries, about −0.1 to −0.3 ms.
- That puts recording near 4.0–4.2 ms: borderline against 4.17.
- GPU + present (GPU 2.5–2.7 ms plus the 1.4 ms present call) is then the
  next limit.
- Plan 3 is necessary but probably not sufficient alone.

**Effort and risk.** About six sessions. Races between stages are the main
hazard, as in Phase 4 milestones 2–6; each milestone's single-thread gate is
the defence.

## Other open items (ranked)

1. **The in-game present call (1.3–1.5 ms; 0.2 ms in the probe).** Ruled out:
   - swapchain usage flags, image format and count, window size and mode;
   - the executable name, the window message pump;
   - the next frame's GPU work (holding the submit changed nothing);
   - device allocation count;
   - the present queue family;
   - Vulkan overlay layers (user: stop there).

   Whatever remains is inside the game process.
2. **GPU frame** (2.35–2.7 ms). The biggest passes are GBuffer (about 0.95),
   HBAO 0.21, postprocess 0.19, cascades 0.22, shadow resolve 0.15. Async
   compute would need compute rewrites of stock pixel shaders (parity risk).
3. **Recording chain:** laps about 3.5 ms. The largest remaining items are:
   - spot shadows, about 0.55 across four laps;
   - probes, about 0.4;
   - the GBuffer main recording, about 0.25.

   The launch gap is about 0.35 ms in waited frames: OLD-cell join, deferred
   replay, `begin_frame`, launch.
4. **Phase 4 milestone 7 remainder:**
   - input-latency measurement;
   - the user plugin set with the split;
   - the split default.
5. **P95 on the render thread** (scheduling, not GC).

## Lessons

- **Price every pacing chain before cutting one.** With three chains near the
  same length, a cut moves the limit; confirm which chain paces (launch gap,
  waited-frame share) first.
- **Find the wait before moving work.** Work removed ahead of a blocking point
  only lengthens the wait. Gates move; they don't vanish.
- **Below about 0.15 ms, only same-session interleaved A/B counts.**
  Cross-session runs here drift 10%.
- **Read the code before planning a cost away.** Check `parallel_*`, cache
  flags and what a scope encloses; two Plan 2 items were wrong from phase
  names alone.
- **A gate must cover what a change touches.** VUID-only scans missed sync
  hazards; the packet signature once missed glass.
- **Identical output doesn't prove a policy ran.** Add a counter (light tiles
  were "off" for a whole batch).
- **Worker jobs must not touch thread-local state** of the thread that
  started them.
- **Never build or deploy during a batch**, and check for other load (Codex,
  other sessions, games) first.
- **Judge lighting only in the same-process frozen-light lane.**
- **Separate cycles from wall time** (`QueryThreadCycleTime`): rising cycles
  mean contention, flat cycles with rising wall time mean preemption.
