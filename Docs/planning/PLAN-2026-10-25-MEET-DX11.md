## Why DX11 is at 4.6 ms

Stock `MyRenderScheduler` (VRage.Render11) builds a dependency graph of jobs
each frame:

- cull jobs per view;
- `GeometryRenderer.Preprocess`;
- `GeometryRendererOld.UpdateCullProxies` and `Prepare`;
- render jobs on deferred contexts;
- foliage, lights, GBuffer resolve, occlusion and transparency.

It runs them on worker threads, and the render thread only joins. In the
Oct 7 ETW capture, DX11's render thread used **2.68 ms of CPU in a 4.11 ms
frame**. It allocated 15 MB over the window; Vulkan allocated 741 MB. State
changes from messages also run on a separate task (`ProcessStateChanges`).

Vulkan's managed `Draw` is mostly serial, single-threaded scene
reconstruction. Native recording runs on one more thread. That is the
structural difference to close.

## The three walls

With pipelined recording, cadence ≈ max(render thread, recording worker,
GPU) plus sync slack. All three must reach about 3.6 ms mean with tight tails:

| Wall | Now | Budget | Cut needed |
|---|---|---|---|
| Render thread: Draw→Present (10.5–10.7) plus 0.8 ms outside it | ≈11.4 ms | ≤3.6 ms | **−7.8 ms** |
| Recording worker (`end_frame`) | ≈4.9 ms | ≤3.5 ms | −1.4 ms |
| GPU, full frame | 3.22–3.34 ms | ≤3.6 ms | none yet; protect the margin |

The P95 is its own problem. Today's profile, unchanged since Oct 21:

- messages P95 4.9 ms against a 0.83 ms mean;
- 17% of frames had a GC;
- the render thread allocates **1.32 MB per frame**: voxels and billboards
  421 KB, scene 404 KB, messages 221 KB, pass publication 172 KB.

## Lessons that constrain the plan

- Caches, byte copies and extra workers around per-frame reconstruction did
  not pay (view eligibility, view plans, static recipe objects, retained
  object hashing, owned preparation). Remove the per-frame O(N) work; do not
  make it cheaper.
- Judge a change by the wall it moves. Recording-worker changes show no
  cadence gain while the render thread is the wall; parallel spots were
  rejected on Oct 8 for that reason.
- Trace samplers mislead here; size candidates with `-CpuDetail` wall phases
  and confirm with paired runs in both orders.
- Run-Isolated zeroes every toggle it knows. Always pass the product flag set.
- Judge lighting only in the same-process frozen-light lane (Pertam's flashing
  light).
- Check for Codex activity before any timing run.

## Plan

Each item lists its expected gain, the gate and the risk. Gains are estimates
from the phase table and must be confirmed by paired runs.

### Phase 0: instrumentation and regression recovery (first session)

The GPU is under budget today, but nothing attributes its 3.3 ms to passes,
and recording sub-phases are coarse. These items also recover the regression
since 1.3.0.

0.1 **Per-pass GPU timestamps.** `frame_mark` already names about 40 passes.
Behind `SE_VULKAN_GPU_PASS_TIMING=1`, write `vkCmdWriteTimestamp2` at each
mark into a per-slot query pool, read it from completed slots only, and
report the per-pass split. No elevation or Nsight needed. Gate: the passes
sum to the existing full-frame `GpuMs` within noise.

0.2 **Recording sub-phases.** Split `prepare_us` (geometry, upload,
materials/descriptors, sort, cascade casters, indirect, spot fades,
opaque reference) and `main_us` (OLD main, NEW main, foliage, object motion,
attachments). `performance.*_us` partly exists; publish it in the profile
report.

0.3 **Message census.** Per `MyRenderMessageEnum`: count, total time, and time
on the slowest 5% of frames. This attributes the 5 ms message P95.

0.4 **Bisect the 1.3.0 → HEAD regression** with archived binaries
(`-BenchmarkPlugin/-BenchmarkNative`), in DX11-normalized pairs. Suspects:
GBuffer velocity, object motion and attachments run whenever any
velocity-capable pipeline is loaded (`gbuffer_velocity_begin`,
`render_object_motion`), not when a consumer exists. Check whether anything
in stock Pertam (no DLSS, FSR or Anomaly pack) reads them; if not, skip them
without a consumer.

0.5 **Find the 0.8 ms outside Draw→Present.** In every uninstrumented
Vulkan run, the present interval exceeds render-thread Draw→Present time by
0.80–0.84 ms. DX11's gap is 0.05 ms. Something in SE's render loop between
`Present` and the next `Draw` costs more under Vulkan: the window update, the
frame waiter, the sync event, or a harness or plugin hook. Add CpuDetail
scopes there. If it is removable, this is the cheapest 0.8 ms in the plan.

0.6 **Diagnostics overhead A/B.** Every frame mark calls
`vkCmdSetCheckpointNV`. The device enables NV diagnostics config with
resource tracking and `robustBufferAccess` unconditionally. Test them behind
one env switch; keep crash recovery working with a cheaper default (for
example, checkpoints only after a recorded crash, or under validation).

### Phase 1: render-thread wins that need no new architecture (target ≈8.5 ms)

1.1 **Zero-allocation frame** (1.33 MB/frame → <64 KB). Sources include:
`BuildNativeViews` (`List`, `views.ToArray()`, `PlaneD[]` per view),
`new NativePassQueryResult[]`, `frameShadowExclusions.ToArray()`, voxel
`actors.Values.ToArray()`, billboard and flare arrays, sprite packet arrays,
and message payload copies. Use pooled arrays and spans. Expected: P95 −2 to
−4 ms, mean −0.3 to −0.6 ms. Gate: allocation counter per phase, GC-tagged
frames <1%.

1.2 **Message dispatch and spikes.** `Process` sends every message through
about nine handler probes (probes, shadows, decals, particles, environment,
voxels, media, sprites, scene) before its switch. Replace that with a table
by message type built once. Then fix whatever the 0.3 census shows behind
the P95 spikes (likely batched object updates or clipmap work landing on one
frame). Expected −0.2 to −0.4 ms mean, a large P95 cut.

1.3 **Start native pass preparation early.** `PreparePassFrame` (0.48 ms)
runs after traversal, voxels and lighting setup, and needs only the views
(camera, cascades, probe faces, spots). Build the views right after
`shadows.Update` and run prepare on the native background worker during
managed traversal. Join at `GetPassPreparation`. Expected −0.4 ms. Gate:
publish benchmark signature unchanged, native-pass lane byte-identical.

1.4 **Stop visiting native-owned actors (T2).** About 2,700 of 3,714
candidates are native-owned and are visited only to declare main-group
owners (query 0.35, plan 0.33, declare 0.56). Steps:

1. Give native-owned actors their main-group token at commit.
2. Let native assign main-group order by the same first-appearance rule.
3. Keep native-owned actors out of the managed candidate index.

Step 1 needs a deterministic-order toggle and its own frozen-light lane,
because group order is spatial-query order today. Expected −1.0 to −1.3 ms.

### Phase 2: render-thread structure (target ≈5.5 ms)

2.1 **Per-subsystem frame emitters.** `NativeBackend` (the graph's largest
god node: 859 edges over about 60 partial files) holds the per-frame
emission state shared by every producer: `worldPackets`, the main-group,
packet-owner and logical-owner scopes, and order counters. That shared
mutable state stops subsystems from running concurrently. Give each producer
its own emitter (packets, owner, order) and merge them in a fixed order at
`QueueWorld`, so the merged list equals today's serial order. This is the
prerequisite for 2.2.

2.2 **Fork-join job graph, DX11 style.** After messages and scene update,
run independent producers in parallel: voxel cull and emission (0.93 ms),
particles (0.32), decals, billboards and flares, the lighting and probe
setup, and the managed actor traversal. Join, merge emitters, publish.
Expected −1.2 to −1.8 ms on 8 cores. Gate: byte-identical merged packet
signature against serial.

2.3 **Native-resident voxel cells**, as native OLD cells did: commit cell
draws on mesh or LOD change; native culls and emits. Removes the per-cell
managed loop and most of the 420 KB/frame. Expected −0.6 to −0.9 ms.

2.4 **O(changes) scene update**: spatial index refresh (0.43), transforms
(0.23) and shadow poses (0.11) touch only dirty actors. Native pass and
cells already receive pose commits, so the managed copies can stop tracking
native-owned actors. Expected −0.3 to −0.5 ms.

2.5 **Remaining publication.** Selection stays synchronous (0.67 ms) because
managed code reads fallbacks and glass tickets right away. Move consumers
that can wait (glass tickets, fallback replay) after the join, so selection
can run on the job graph too.

### Phase 3: recording worker below 3.5 ms

3.0 **Per-worker descriptor allocation (prerequisite).** Parallel spot
recording exists, but `render_spot_shadows` turns it off whenever the native
pass scene is ready (the product default). Native-pass views allocate
descriptor sets from one shared per-slot pool, so spots (0.77 ms) record
serially. Give each recording worker its own per-slot descriptor pool, or
allocate and write pass-view descriptors before recording starts. This
re-enables parallel spots and is required for 3.1. Expected −0.4 to −0.5 ms
of recording time.

The Oct 8 parallel-spots rejection (`Performance-2026-10-08-ParallelSpotsRejection.md`)
measured whole-frame time when recording was serial on the render thread
and not the limiting cost. Judge 3.0 by recording-worker time until recording
becomes the wall, then by cadence.

3.1 **Parallel main-pass recording.** Cascades already record into secondary
command buffers on workers. Do the same for the GBuffer: split OLD phases
and the NEW selection into contiguous ranges, record them into secondaries
in parallel, and execute them in order, so draw order is unchanged.
Expected main 1.65 → about 0.6 ms.

3.2 **Prepare (1.54 ms).** Reuse material descriptor sets across frames by
material key (or move to descriptor buffers or push descriptors). Keep the
sort keys and order when the draw set is unchanged; otherwise use a radix
sort on packed keys. Resolve materials in parallel ranges. Expected −0.6 to
−0.8 ms. Gate: identical draw order signature.

3.3 **Overlap spots, cascades and main.** Spot secondaries, cascade
secondaries and main secondaries are independent until the primary executes
them. Start all of them before the primary needs any.

3.4 **Persistent worker pool** in place of per-frame `std::async`
(cascades, upload copy), to avoid thread churn and get stable tails.

### Phase 4: the third pipeline stage (from ≈5.5 ms to below 4.17 ms)

Phases 1–3 make the render thread mostly messages, deltas and joins. The last
step moves frame building (selection, LOD, culling, packing and the managed
fallbacks) onto a frame-build worker. The render thread then processes frame
N+1's messages while the worker builds frame N and the recorder records N−1.

- The pipelined-recording design already provides the mechanism: deferrable
  calls copy their arguments, snapshot calls answer from a launch snapshot,
  and everything else waits.
- The frame builder needs an immutable view of actor state. Native-owned
  actors already have one (commits). Managed fallbacks (glass, skinned, old
  decals, unsupported) need a snapshot or must become native first.
- Cost: one frame of added latency, as with pipelined recording. Measure
  input-to-present latency and keep a toggle.

Expected: render thread ≈ messages + deltas + joins, about 2–2.5 ms; cadence
bound by the recording worker or GPU.

### Phase 5: GPU margin (scope set by 0.1)

The GPU frame fits the budget today. This phase protects the margin as parity
features land and cuts tails. Candidates once pass timings exist:

- skip velocity, motion and attachments with no consumer (0.4);
- diagnostics and robustness off (0.6);
- async compute for light tiles, SSAO/HBAO and histogram;
- spot and cascade caching under the stock schedule.

Do not optimize shaders before pass attribution exists.

### Phase 6: tails and acceptance

- P95 below 4.17 ms needs a GC-free frame (1.1), no message spikes (1.2), and
  shadow and probe updates amortized evenly across frames.
- Three both-order pairs, 45 s warmup / 30 s sampling, mean and P95
  below 4.17 ms.
- Parity gates: frozen-light lane per toggle, validation-layer gameplay run,
  native CTests, focused GPU suites; full GPU set only at milestones.

## Method (unchanged)

1. Fresh `-CpuDetail -NativeCritical` profile first; check the pipeline
   report for waits.
2. Judge throughput by `PresentMs` or the interval mean, never `CpuMeanMs`
   alone.
3. Paired interleaved runs in both orders (NP, X, X, NP); host noise is
   about ±1 ms. Normalize across days with a DX11 run.
4. One toggle per change, default on only after its gates pass.
5. Product-default flags: `-ActorLods -AsyncPresent -NewActorViews
   -RetainedSubmission -StockShadowSchedule -StockShadowFit -WorldRecipes
   -ParallelQueue -ParallelCascades -NativePassScene -GroupOcclusion
   -StockDepthGeometry -NativeCells -NativeMixedOpaque -PipelinedRecording
   -AsyncPassPacking -DeferredCellEmission`.
